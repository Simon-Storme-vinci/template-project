1 Introduction

1.1 Objectif

Ce projet met en place un reverse proxy avec gestion automatique des certificats. Nous utiliserons “Let’s Encrypt”, “Traefik” et Docker.

Traefik est le point d’entrée unique du serveur et du client : il reçoit les connexions sur les ports 8080 et 8443 redirigés vers 80 et 443 dans le conteneur, route chaque requête vers le bon conteneur Docker selon le nom de domaine, et sert tout en HTTPS avec des certificats Let’s Encrypt qu’il obtient et renouvelle lui-même, sans intervention humaine.

1.2 Contexte et problématique

Sans reverse proxy, le serveur applicatif est exposé directement sur Internet, ce qui pose des problèmes de sécurité et de flexibilité. L’automatisation de certificats permet de ne plus se soucier de l’expiration, mais une supervision reste utile comme filet de sécurité.

2.1 Interfaces réseau VirtualBox

Chaque VM dispose de deux interfaces réseau dans VirtualBox :

Interface Type VirtualBox Rôle
eth0 (enp0s3) NAT Télécharger les images Docker, installer les logiciels et contacter Let’s Encrypt
eth1 (enp0s8) Host-only (vboxnet0) Communication entre la VM et avec la machine hôte
Note

Pourquoi host-only et pas “réseau interne” ?

Le réseau interne (intnet) isole les VMs entre elles mais la machine hôte ne peut pas les joindre. Le host-only crée le réseau 192.168.56.0/24 partagé entre les VMs et l’hôte (192.168.56.1) : on peut ainsi ouvrir https://projetinfra.duckdns.org:8443 dans le navigateur de l’hôte, et le correcteur peut faire de même depuis sa propre machine en reproduisant le TP.

Réglage VirtualBox : Paramètres de chaque VM → Réseau → Carte 2 → Réseau privé hôte (host-only) → vboxnet0. Si vboxnet0 n’existe pas : Fichier → Outils → Gestionnaire de réseau → Créer.

Note

Pourquoi garder la carte NAT ?

Traefik doit contacter, en sortie, les serveurs de Let’s Encrypt et l’API de votre hébergeur DNS pour obtenir les certificats (défi DNS-01). Le NAT fournit cet accès Internet sortant. Aucune connexion entrante depuis Internet n’est nécessaire : le fichier hosts de la machine hôte associe le nom à 192.168.56.10, et DuckDNS sert uniquement à créer l’enregistrement TXT du défi DNS-01.

2.3 Configuration des IPs fixes

Avant de lancer Debian : 1. Clic droit sur Debian 2. Sélectionner “Configuration” 3. Aller dans “Réseau” 4. Aller dans “Adaptateur 2”, puis cochez la case “Activer l’interface réseau” tout en haut. 5. Dans le menu déroulant “Attached to” (Rattaché à), sélectionnez “Host-only Adapter” (Réseau privé hôte). 6. Dans le champ “Name” qui va alors s’éclairer et devenir cliquable, sélectionnez vboxnet0. 7. Cliquez sur OK en bas pour valider.

Sur vm-proxy, éditer /etc/network/interfaces :

nano /etc/network/interfaces
# Interface host-only — IP fixe
auto enp0s8
iface enp0s8 inet static
    address 192.168.56.10
    netmask 255.255.255.0

Vérifier que le service networking est actif et que la configuration utilise bien ifupdown.

Appliquer la configuration (de préférence depuis la console VirtualBox) :

systemctl restart networking

# Vérifier spécifiquement l'interface host-only : 
ip a show enp0s8
# Le résultat attendu est => inet 192.168.56.10/24 ...

Note

Les trois conteneurs Nginx communiquent avec Traefik via un réseau Docker interne. Le port 80 de chaque conteneur n’est pas directement exposé sur le réseau Host-only : les utilisateurs accèdent uniquement au service à travers Traefik, sur les ports 8080 (HTTP) et 8443 (HTTPS).

La VM vm-proxy dispose également d’une interface NAT pour accéder à Internet, notamment pour télécharger les images Docker et communiquer avec Let’s Encrypt.

Les informations du client sont transmises aux serveurs NGINX : Traefik ajoute notamment les en-têtes X-Forwarded-For et X-Forwarded-Proto, qui permettent aux serveurs web de connaître l’adresse IP du client et le protocole utilisé à l’origine.

5.4 Configuration de Traefik et de Let’s Encrypt (sur vm-proxy)

Pourquoi : Traefik constitue le cœur de notre projet. Il reçoit les connexions HTTP et HTTPS, sélectionne le serveur web correspondant au nom de domaine demandé et assure la terminaison TLS. Il communique également avec Let’s Encrypt pour obtenir et renouveler automatiquement les certificats.

Dans notre projet, nous utilisons le challenge DNS-01 de Let’s Encrypt. Celui-ci permet de valider notre nom de domaine grâce à un enregistrement DNS TXT, sans devoir exposer directement notre VM sur Internet.

5.4.1 Créer le sous-domaine DuckDNS et préparer les identifiants

Pourquoi : le challenge DNS-01 oblige Traefik à créer un enregistrement TXT dans la zone DNS du domaine, ce qui prouve à Let’s Encrypt que nous en sommes bien propriétaires. Il nous faut donc un nom de domaine dont nous contrôlons le DNS par une API. Nous avons choisi un sous-domaine gratuit DuckDNS, pour lequel Traefik dispose d’un fournisseur intégré (duckdns). Un sous-domaine de github.io ne convient pas : sa zone DNS appartient à GitHub, nous ne pouvons pas y créer d’enregistrement TXT.

  1. Se connecter sur duckdns.org avec un compte GitHub ou Google.
  2. Dans le champ « sub domain », saisir projetinfra puis cliquer sur « add domain ». Le domaine obtenu est projetinfra.duckdns.org.
  3. Copier le token affiché en haut de la page.

Sur vm-proxy, créer le fichier .env à la racine du projet, dans le même dossier que docker-compose.yml :

cd ~/projet-proxy
nano .env

Y ajouter la ligne suivante en remplaçant la valeur d’exemple par le token copié (sans guillemets ni espaces autour du =) :

DUCKDNS_TOKEN=VOTRE_TOKEN_DUCKDNS

Ce fichier contient un secret : il ne doit être ni partagé ni ajouté à un dépôt Git. Le protéger :

chmod 600 .env

Vérification :

ls -la .env

Résultat attendu : les droits -rw------- (lecture et écriture réservées au propriétaire).

Le fichier est transmis à Traefik par la directive env_file: - .env du service traefik dans docker-compose.yml. Une fois les conteneurs démarrés, on peut confirmer que la variable est bien reçue :

docker exec traefik env | grep DUCKDNS

5.4.2 Préparer le stockage des certificats

Créer le fichier qui permettra à Traefik de conserver les certificats obtenus auprès de Let’s Encrypt :

touch letsencrypt/acme.json
chmod 600 letsencrypt/acme.json

Ce fichier permet à Traefik de conserver les certificats et les informations ACME nécessaires à leur renouvellement automatique.

5.4.3 Configurer Traefik dans Docker Compose

Créer le fichier principal de déploiement :

nano docker-compose.yml

Ajouter la configuration suivante en remplaçant votre.mail@outlook.com par un mail que vous possédez et projetinfra.duckdns.org par votre véritable nom de domaine :

services:
  traefik:
    image: traefik
    env_file:
      - .env
    container_name: traefik
    restart: unless-stopped
    environment:
      - DOCKER_API_VERSION=1.40
    ports:
      - "8080:80"
      - "8443:443"
    command:
      - --providers.docker=true
      - --providers.docker.exposedbydefault=false
      - --entrypoints.web.address=:80
      - --entrypoints.websecure.address=:443
      - --certificatesresolvers.le.acme.email=votre.mail@outlook.com
      - --certificatesresolvers.le.acme.storage=/letsencrypt/acme.json
      - --certificatesresolvers.le.acme.dnschallenge=true
      - --certificatesresolvers.le.acme.dnschallenge.provider=duckdns
      - --certificatesresolvers.le.acme.dnschallenge.resolvers=1.1.1.1:53

    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - ./letsencrypt/acme.json:/letsencrypt/acme.json
    networks:
      - proxy


  nginx1:
    image: nginx:alpine
    container_name: nginx1
    restart: unless-stopped
    volumes:
      - ./site/nginx1:/usr/share/nginx/html:ro
    networks:
      - proxy
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.site.rule=Host(`projetinfra.duckdns.org`)"
      - "traefik.http.routers.site.entrypoints=websecure"
      - "traefik.http.routers.site.tls.certresolver=le"
      - "traefik.http.services.site.loadbalancer.server.port=80"
  nginx2:
    image: nginx:alpine
    container_name: nginx2
    restart: unless-stopped
    volumes:
      - ./site/nginx2:/usr/share/nginx/html:ro
    networks:
      - proxy
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.site.rule=Host(`projetinfra.duckdns.org`)"
      - "traefik.http.routers.site.entrypoints=websecure"
      - "traefik.http.routers.site.tls.certresolver=le"
      - "traefik.http.services.site.loadbalancer.server.port=80"

  nginx3:
    image: nginx:alpine
    container_name: nginx3
    restart: unless-stopped
    volumes:
      - ./site/nginx3:/usr/share/nginx/html:ro
    networks:
      - proxy
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.site.rule=Host(`projetinfra.duckdns.org`)"
      - "traefik.http.routers.site.entrypoints=websecure"
      - "traefik.http.routers.site.tls.certresolver=le"
      - "traefik.http.services.site.loadbalancer.server.port=80"

networks:
  proxy:
    external: true

Dans cette configuration :

  • Traefik écoute sur les ports 80 et 443.
  • Les trois conteneurs Nginx ne publient aucun port directement sur la VM.
  • Les conteneurs communiquent grâce au réseau Docker proxy.
  • Traefik utilise le fournisseur Docker (labels) pour découvrir les trois serveurs web.
  • Le résolveur ACME utilise le challenge DNS-01 de DuckDNS pour obtenir les certificats Let’s Encrypt.

Vérification de la configuration :

docker compose config -q

Si aucune erreur n’est affichée, le fichier Docker Compose est syntaxiquement valide.

5.7 Configuration de la résolution DNS locale (sur la machine hôte)

Pourquoi : notre VM utilise une adresse privée Host-only. Pour accéder au site depuis le navigateur de la machine hôte, nous devons faire correspondre notre nom de domaine à l’adresse IP privée de la VM.

Sur la machine hôte, ajouter la ligne suivante au fichier hosts :

192.168.56.10 projetinfra.duckdns.org

Emplacement du fichier selon le système :

  • Linux/macOS : ```bash nano /etc/hosts
- Windows : ```bash
notepad C:\Windows\System32\drivers\etc\hosts

N’oubliez pas de sauvegarder les modifications du fichier (CTRL + S ou autre)

Remplacer le nom de domaine par celui configuré dans les labels de docker-compose.yml.

Cette résolution locale permet au navigateur de joindre Traefik sur 192.168.56.10, tout en utilisant le véritable nom de domaine pour la négociation HTTPS.

Il n’est pas nécessaire de publier l’adresse privée de la VM dans un enregistrement DNS public A pour utiliser le challenge DNS-01.

5.8 Vérification de l’obtention du certificat Let’s Encrypt (sur vm-proxy)

Pourquoi : cette étape permet de vérifier que Traefik communique correctement avec Let’s Encrypt, que le challenge DNS-01 fonctionne et qu’un certificat valide est obtenu automatiquement.

Consulter les journaux de Traefik :

docker logs traefik

Traefik doit réussir la validation DNS et obtenir un certificat pour le domaine configuré.

Vérifier ensuite le contenu du fichier ACME :

grep -o '"main": "[^"]*"' letsencrypt/acme.json

La commande doit montrer “main”: “projetinfra.duckdns.org”

Pour vérifier le certificat depuis la machine hôte dans un terminal bash :

openssl s_client \
  -connect 192.168.56.10:8443 \
  -servername projetinfra.duckdns.org \
  </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates

Le résultat doit afficher :

  • Le nom de domaine correspondant au certificat.
  • Let’s Encrypt comme autorité de certification.
  • Les dates de début et de fin de validité du certificat.

Le certificat doit être reconnu comme valide par un navigateur utilisant son magasin de certificats habituel.

Attention : Let’s Encrypt peut limiter le nombre de certificats émis lors des tests répétés. Il est conseillé d’utiliser son environnement de test (staging) pendant les essais de configuration, puis de revenir à l’environnement de production pour obtenir le certificat final.

7 Problèmes rencontrés

ImportantConsigne

Décrivez les 2 à 4 problèmes qui vous ont le plus bloqués, avec la structure Symptôme / Cause / Solution. Cette section montre votre compréhension réelle du projet — elle doit refléter ce qui s’est réellement passé dans vos VMs.

1. Perte de la connexion PuTTY après le redémarrage du réseau

Symptôme : après systemctl restart networking, PuTTY n’affichait plus qu’un écran noir. Dans la console VirtualBox, ip a ne montrait plus enp0s8 avec son adresse, et ifup enp0s8 répondait « unknown interface ».

Cause : le fichier /etc/network/interfaces ne contenait plus que les interfaces lo et enp0s3 : le bloc enp0s8 (adresse statique 192.168.56.10) avait disparu. L’interface host-only n’avait donc plus de configuration et la VM n’était plus joignable depuis la machine hôte.

Solution : à partir de la console VirtualBox (qui ne dépend pas du réseau), nous avons rajouté le bloc auto enp0s8 / iface enp0s8 inet static avec l’adresse 192.168.56.10 et le masque 255.255.255.0, sans ligne gateway, puis relancé le service networking.

2. Réseau Docker proxy introuvable

Symptôme : docker compose up -d échouait avec network proxy declared as external, but could not be found.

Cause : le réseau proxy est déclaré avec external: true. Docker Compose ne crée pas ce type de réseau.

Solution : création du réseau avant le premier démarrage avec docker network create proxy.

3. Certificat par défaut de Traefik au lieu de Let’s Encrypt

Symptôme : curl ne fonctionnait qu’avec l’option -k, et openssl indiquait comme émetteur TRAEFIK DEFAULT CERT.

Cause : la configuration initiale utilisait le défi HTTP-01, qui impose à Let’s Encrypt de joindre le serveur depuis Internet. Notre VM n’a qu’une adresse privée (192.168.56.10), la validation ne pouvait donc pas aboutir et Traefik utilisait son certificat autosigné de secours.

Solution : passage au défi DNS-01 avec le fournisseur DuckDNS (dnschallenge.provider=duckdns) et un token stocké dans .env. Nous avons d’abord testé avec l’environnement de test (staging) de Let’s Encrypt pour éviter les limites de requêtes : ses certificats ne sont pas reconnus par les clients (curl: (60) SSL certificate problem). Après validation, nous avons retiré la ligne caserver, vidé acme.json (pour ne pas réutiliser le compte staging) et redémarré pour obtenir un certificat de production.

4. Résolution DNS impossible depuis les conteneurs

Symptôme : les journaux de Traefik affichaient Unable to obtain ACME certificate ... lookup acme-v02.api.letsencrypt.org ... i/o timeout, et ping 8.8.8.8 échouait depuis la VM alors que enp0s3 avait bien une adresse et une route par défaut.

Cause : le réseau utilisé fournissait par DHCP un serveur DNS interne à l’école (172.19.232.1). Cette adresse tombait dans le sous-réseau 172.19.0.0/16 d’un pont Docker de la VM, si bien que le trafic vers ce serveur restait sur le pont local et n’atteignait jamais le vrai serveur DNS. Le réseau de l’école bloquait par ailleurs le trafic sortant de la VM.

Solution : changement de connexion Internet, après quoi ping acme-v02.api.letsencrypt.org fonctionnait et Traefik a pu obtenir le certificat. Pour éviter le problème, on peut aussi configurer un serveur DNS public (nameserver 1.1.1.1) ou supprimer le réseau Docker qui chevauche l’adresse du DNS.

9 Améliorations possibles

ImportantConsigne

Proposez des améliorations concrètes et réalistes. Évitez les généralités (“on pourrait améliorer la sécurité”) — soyez précis (“on pourrait remplacer le certificat auto-signé par Let’s Encrypt via certbot, ce qui nécessiterait un nom de domaine public”).

  • Redirection automatique de HTTP vers HTTPS : ajouter à la commande de Traefik --entrypoints.web.http.redirections.entrypoint.to=websecure et --entrypoints.web.http.redirections.entrypoint.scheme=https. Aujourd’hui, une requête HTTP sur le port 8080 ne reçoit pas de redirection ; cela garantirait que tout le trafic passe par le HTTPS.
  • Protection du token DuckDNS : remplacer le fichier .env par des secrets Docker (secrets: dans le fichier Compose), afin que le token ne soit pas visible dans les variables d’environnement du conteneur (docker exec traefik env).
  • Ports standard 80 et 443 : publier 80:80 et 443:443 au lieu de 8080 et 8443, afin que l’URL n’ait plus besoin d’un numéro de port. Cela nécessite de libérer ces ports sur la VM.
